# new-api 网关压测进度简报

汇报日期：2026 年 9 月 19 日

## 一句话进展

高并发短请求的承载能力已摸清（并发 6,000、成功率 100%）；长上下文压测发现并修复了两个测试工具链问题，目前正按行业标准方法（长短混合负载）做最终验证，预计还需 1–2 轮测试即可给出可承诺的运营容量数字。

## 已完成的工作

**1. 高并发测试（已完成，结果良好）**

切换到专用压测服务器后重跑：共发起 124,408 次请求，**全部成功（100%）**，并发从 2,000 逐步推到 6,000 无一失败。服务器 CPU 峰值仅 23%、内存 2.4%，资源远未到瓶颈；去掉压力后延迟立即恢复正常。此前一轮约 42% 失败率的问题已确认是旧压测机自身性能不足导致，与网关无关。

关键数字：吞吐在并发 3,000 后稳定在约 325 次/秒；并发 6,000 时 95% 请求在 35 秒内完成（延迟主要是排队，不是故障）。

**2. 长上下文测试（进行中）**

针对百万 token 超长输入的流式请求场景：

- **已修复两个测试工具问题**：测量代理在大输入下内存溢出崩溃（已定位根因、修复并在本地复现验证）；压测客户端发送速率瓶颈（每 VU 重复构建 8MB 请求体，已优化为只构建一次）。修复后 1,000 并发请求全部正常发出、测量数据完整。
- **识别出真实瓶颈**：1,000 个并发各传 8MB 请求体时，实际到达服务器的带宽只有约 5 MB/s，绝大多数请求超时——这是**压测形态问题**（现实中不会有 1,000 个用户同时发百万 token 请求），不代表网关能力。
- **已按行业标准方法改造**：真实流量中大上下文是少数尾部事件，因此改为混合长度负载——70% 短请求（2K token）、20% 中等（32K）、9% 大（128K）、1% 百万 token 尾部，报告按长度分层出指标。该方案已实现并在本地全量验证通过（600 请求、成功率 100%、四层比例精确命中）。

## 下一步计划

1. 用混合长度负载在压测服务器上重跑长流式场景（含 1M token 尾部请求），拿到分层的首字延迟、流完整性和吞吐数据。
2. 补测上传带宽基线（单连接与多并发），确认带宽墙在网络路径哪一层，用于归因和容量修正。
3. 在 2,000–3,000 并发区间做长时间固定负载验证（该区间延迟达标），作为运营容量建议的基础。
4. 待以上数据齐全后输出最终容量结论（预计含建议运营限额、故障恢复验证）。

## 风险与说明

- 当前测试使用模拟上游（Mock），验证的是网关转发链路容量；真实模型供应商的服务能力需上线后另行验证。
- 现有测试均为短时负载（分钟级），长期稳定性（内存泄漏、连接泄漏）需后续浸泡测试确认。
- 测试报告中的环境信息（版本、实例规格、负责人）待补全，最终结论以补全后的报告为准。
